## 🗺️ Текущая карта проекта

В репозитории три типа контента:

**Зрелые, стабильные артефакты:**
- `DONE.ipynb` — основной рабочий ноутбук с финальными результатами

Проект находится в **активной точке развития**: Task 1 и 2 выполнены, Task 3 (кросс-валидация) запланирована, но не реализована. Ветки помогут войти в эту задачу без риска сломать уже работающий код.

## 🎯 План миграции на три ветки

Вот точная последовательность команд для реализации на практике. Предлагаю начать с того, что ты создашь две новые ветки и перераспределишь содержимое.

### Шаг 1. Создать ветки `made` и `sandbox` из текущего `main`

Текущий `main` — это смесь всего. Мы превратим его в чистую релизную ветку, а историю сохраним в двух других:

```bash
git checkout main
git checkout -b mindground   # песочница = полная копия текущего состояния
git checkout main
git checkout -b made      # ветка для стабильной сборки
```

Теперь у тебя три ветки, и все пока указывают на один и тот же коммит.

### Шаг 2. Очистить `main` — оставить только релизный код

Остаёмся в `main`. Удаляем всё, что не является финальным результатом проекта:

```bash
git checkout main
git rm __sandbox.ipynb
git rm tmp.md
git rm "DEEP — Теория по accuracy.md"
git rm "DEEP — Теория по кросс-валидации.md"
git rm "DEEP — Алгоритм псевдослучайных чисел.md"
git rm "curr state.md"
git rm "Pasted image 20260426211115.png"
git commit -m "clean: оставить только релизный код в main"
```

В `main` останутся: `DONE.ipynb`, `ALIGN.md`, `STEP.md`, `README.md`, `requirements.txt`, `.obsidian/`, `.vscode/`.

### Шаг 3. Очистить `made` — привести к стабильно-рабочему состоянию

```bash
git checkout made
git rm __sandbox.ipynb
git rm tmp.md
git commit -m "clean: оставить только стабильные артефакты в made"
```

В `made` будут: `DONE.ipynb`, `ALIGN.md`, `STEP.md`, `README.md`, `requirements.txt`, `.obsidian/`, `.vscode/`, а также все три DEEP-файла и `curr state.md`. Это компромисс: в `made` хранятся не только финальные результаты, но и теоретическая база, на которую можно опираться при доработках. Их можно будет удалить позже, когда проект перейдёт в `main`.

### Шаг 4. Песочница — оставить как есть

Ветка `sandbox` уже содержит всё, включая `__sandbox.ipynb` и `tmp.md`. Ничего удалять не нужно. Это твоя неприкосновенная «живая картография».

### Шаг 5. Итоговая картина

После миграции структура будет такой:

| Ветка     | Содержит                                                             | Назначение                                                                           |
| --------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `sandbox` | **Всё** из текущего `main` + маркеры + черновики                     | Территория экспериментов. `tmp.md` и `__sandbox.ipynb` живут здесь, пока не созреют. |
| `made`    | `DONE.ipynb`, `STEP.md`, `ALIGN.md`, DEEP-файлы, `curr state.md`     | Стабильный прототип. Место для Task 3: добавляешь кросс-валидацию, не трогая `main`. |
| `main`    | `DONE.ipynb`, `STEP.md`, `ALIGN.md`, `README.md`, `requirements.txt` | Чистовой, релизный код. То, что можно показать как готовый проект.                   |

## 🔄 Как это будет работать для твоей следующей задачи (Task 3 — кросс-валидация)

Вместо того чтобы бояться сломать работающий код в `DONE.ipynb`, ты:

1. Переключаешься в `sandbox`:
   ```bash
   git checkout sandbox
   ```
2. Экспериментируешь с кросс-валидацией, добавляешь новые ячейки, пробуешь разные подходы. Файлы `tmp.md` и `__sandbox.ipynb` — твоё рабочее пространство.
3. Когда решение найдено и отлажено — копируешь итоговые блоки в `DONE.ipynb` **в ветке `made`**:
   ```bash
   git checkout made
   # вносишь изменения в DONE.ipynb
   git add DONE.ipynb
   git commit -m "feat: add cross-validation results (Task 3, migrated from sandbox)"
   ```
4. Когда весь проект протестирован и готов — делаешь Pull Request из `made` в `main` или просто:
   ```bash
   git checkout main
   git merge made
   ```

## 📎 Якоря в файлах

При переносе результатов из песочницы в `made` — добавляй в docstring или в markdown-ячейку ссылку на исходный черновик:

```markdown
> Разработано в песочнице: см. `__sandbox.ipynb` (ветка `sandbox`), ячейки 12–18.
```

Технически это остаётся копипастом, но с прозрачной связью между «живой картографией» и чистовым кодом.

## 📁 Про твои папки и названия

Твоя структура (`ALIGN.md`, `STEP.md`, `DEEP — ...`) полностью сохраняется во всех трёх ветках. Ветки не диктуют имена файлов — они лишь определяют **стадию зрелости** их содержимого. Ты можешь продолжать использовать специфичные названия и маркеры — они будут работать точно так же, как и раньше, но теперь ты всегда знаешь, в какой ветке искать ту или иную версию.
