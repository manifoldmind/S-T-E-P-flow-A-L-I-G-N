# Система маркеров для комментариев в коде

Этот файл — справочник по стандартным тегам, которые мы используем в комментариях `//`, `#`, `/* */`.  
Цель — быстрое понимание статуса, истории и назначения любого блока кода при чтении.

---

## 🔖 Планирование и задачи

| Маркер       | Значение                                                                             | Пример использования                                      |
| ------------ | ------------------------------------------------------------------------------------ | --------------------------------------------------------- |
| `# TODO:`    | Точно сформулированная задача на будущее, которую нужно сделать позже                 | `// # TODO: Добавить обработку ошибок сети`               |
| `# BACKLOG:` | Идея или набросок, который планируется развить в будущих итерациях                    | `// # BACKLOG: Реализовать кэширование для этого запроса` |
| `# PLAN:`    | Зафиксированный план действий (что и зачем будем менять)                              | `// # PLAN: Сначала вынести валидацию в отдельный хелпер` |
| `# MAKEME:`  | Указание (себе или коллеге) **реализовать** конкретную функцию                        | `// # MAKEME: Дописать парсинг даты из ответа API`        |

---

## 🛠️ Исправление и рефакторинг

| Маркер       | Значение                                                                                                                                    | Пример использования                                         |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| `# FIXME:`   | Код работает, но содержит известную проблему / баг / неоптимальность. Задано неоптимальное решение, которое стоит поправить                  | `// # FIXME: При большом числе записей будет тормозить`      |
| `# HACK:`    | Временное или неочевидное решение, которое нужно будет заменить                                                                             | `// # HACK: Обход бага в версии библиотеки 2.1.0`            |
| `# REFACT:`  | Место требует конкретного рефакторинга (переименование, выделение функции и т.п.)                                                           | `// # REFACT: Вынести дублирующийся цикл в утилиту`          |
| `# FIXED:`   | Маркер для закрытого `# FIXME:` (можно удалить, но иногда оставляют для истории)                                                            | `// # FIXED: Убрал утечку памяти, теперь контекст очищается` |

## 🧪 Временное, отладочное и процессное

| Маркер     | Значение                                                                                                              | Пример использования                                                                                                    |
| ---------- | --------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `# DEBUG:` | Код только для отладки, не должен попасть в продакшн                                                                  | `// # DEBUG: console.log('Значение переменной:', data);`                                                                |
| `# TMP:`   | Временный код, который будет удалён после тестирования идеи                                                           | `// # TMP: Жёстко зашитый ID для проверки запроса`                                                                      |
| `# STUB:`  | Заглушка / фундамент для будущей логики, сейчас не используется (потенциальный концепт)                               | `// # STUB: Метод пока возвращает null, допишу позже`                                                                   |
| `# QUE:`   | Конкретный вопрос к части кода (себе или коллегам). Ожидает ответа `# ANS:`                                           | `// # QUE: Почему мы разбиваем этот блок на 2 отдельных класса?`                                                        |
| `# ANS:`   | Ответ на вопрос `# QUE:`. Содержит отсылку к теории, шаблону или методу, а не к конкретной реализации в коде           | `// # ANS: Принцип разделения интерфейсов (ISP), чтобы не тащить лишние зависимости`                                    |
| `# PROC:`  | Закладка-маркер, сообщающая, что блок находится в процессе разработки (WIP). Удаляется перед коммитом в основную ветку | `// # PROC: Дописываю логику обработки ошибок`                                                                          |

## 📌 Особые пометки (защита от удаления / важные пояснения)

| Маркер      | Значение                                                                                                                                                                                  | Пример использования                                          |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| `# NOTE:`   | Важное пояснение к фрагменту. Описывает логику работы кода, почему сделано именно так                                                                                                    | `// # NOTE: Порядок вызовов критичен из-за состояния гонки`   |
| `# WARN:`   | Требуется внимание к потенциальным *неочевидным* проблемам. По сути — готовый ответ на вопрос, который мог бы возникнуть у читающего код                                                  | `// # WARN: Не менять порядок аргументов, иначе упадёт в рантайме без ошибок компиляции` |
| `# KEEP:`   | Прямое указание не удалять этот блок (даже если кажется ненужным)                                                                                                                         | `// # KEEP: Используется в тестах через рефлексию`            |
| `# SOLVED:` | Ход решения конкретной проблемы описан в комментарии (для истории). Фиксирует инженерное решение                                                                                           | `// # SOLVED: Проблема с таймаутом решена увеличением до 30с` |
| `# DONE:`   | Закладка-маркер, сообщающая, что микро-задача завершена в рамках более крупной работы (контрольная точка истории)                                                                         | `// # DONE: Валидация email через regex`                      |

## 🤔 Неочевидные / глубокие пометки

> [!question] Зачем и где нужны?
> Для описания / утверждения решений, состоящих не только из кода, но из возможных альтернативных сложносоставных подходов: концептуальных + инженерных + скриптовых.
> Может быть полезно не в самом коде, а в документации / черновиках, фиксирующих процесс попыток решений.

| Маркер    | Значение                                                         | Возможный пример                                                 |
| --------- | ---------------------------------------------------------------- | ---------------------------------------------------------------- |
| `# GROK:` | Место, где нужно "въехать" в сложную логику, понять суть         | `// # GROK: Здесь магия с замыканиями, разберись перед правками` |
| `# DEEP:` | Требуется глубокое погружение в тему / документацию / спецификацию | `// # DEEP: Поведение этого флага описано в RFC 1234`            |

## 💡 Рекомендации по использованию

- Старайся использовать маркеры **в начале строки комментария** для быстрого поиска (`Ctrl+F "# TODO"`).
- В больших проектах можно настроить подсветку маркеров в IDE (например, плагин **Todo Tree** для VSCode).
- **Жизненный цикл:**
  - `# PROC` и `# DEBUG` должны быть удалены перед слиянием в основную ветку.
  - `# QUE` должен быть заменён на `# ANS` или удалён после получения ответа.
  - `# TODO` / `# FIXME` после выполнения заменяются на `# DONE` / `# FIXED` или удаляются.
