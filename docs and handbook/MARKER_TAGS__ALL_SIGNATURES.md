# MARKER TAGS: SIGNATURES for PROCESSING and DEVELOPMENT

Сводный справочник всех стандартных тегов-маркеров формата `# TAG: описание`,  
используемых в комментариях к коду, в документации и черновиках.

Цель — единая система меток для быстрого понимания статуса, слоя мышления и назначения любого фрагмента.
Все теги пишутся **в начале строки** с заглавными буквами и двоеточием.

>[!important]
>Важно понимать, что теги носят рекомендательный характер — они необязательны, а иногда даже чрезмерно детальное их использование *запутывает и вредит* ходу работы (особенно поначалу и это — НОРМАЛЬНО). Поэтому рекомендуется просто зафиксировать наиболее простые теги и использовать их в случае <ins>необходимости</ins> (когда исполнитель **часто** сталкивается с потребностью зафиксировать некоторые шаги, помечать заметками и т.д.).
>
> Также **не** запрещается путать близкие по смыслу теги типа `BACKLOG` и `IDEA`, `DONE` и `MAKED`, `GROK` и `DEEP`, `REFACT` и `REDEF` и любые другие совпадения.
>
> Маркеры должны <ins>упрощать</ins> работу по максимуму, а не тормозить её и усложнять. Самое главное, чтобы было **понятно для всех разработчиков** проекта и чтобы в случае чего можно было **быстро вернуться** к необходимым частям работы и вспомнить основной последний контекст.

## Класс 1. Повествовательные теги

> Всегда требуют поясняющего комментария. Фиксируют ход мысли, объяснение или диалог.  
> Столбец «Слой»: `tech` — техническая реализация; `context` — контекст задачи; `any` — универсальный.

| Маркер        | Слой      | Назначение                                                                                                  | Пример                                                                                                            |
| ------------- | --------- | ----------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `# NOTE:`     | `tech`    | Пояснение технического решения, архитектуры, взаимодействия частей кода.                                    | `// # NOTE: Мьютекс нужен из-за общего состояния пула потоков`                                                    |
| `# WARN:`     | `tech`    | Предупреждение о потенциальной технической ловушке (гонка, скрытые зависимости, хрупкий код).               | `// # WARN: Не менять порядок аргументов, иначе упадёт в рантайме`                                                |
| `# HACK:`     | `tech`    | Временное или неочевидное техническое решение, которое нужно будет заменить.                                | `// # HACK: Обход бага библиотеки v2.1.0`                                                                         |
| `# ANALYZED:` | `context` | Результат анализа задачи или бага «на языке пользователя»: что происходит с точки зрения логики, а не кода. | `// # ANALYZED: Шахматы сдвинулись влево из-за неверной нумерации колонок`                                        |
| `# IDEA:`     | `context` | Сырая продуктовая идея (не техническая). Может позже стать `# BACKLOG:` или `# PLAN:`.                      | `// # IDEA: Подсвечивать кнопку градиентом при наведении`                                                         |
| `# QUE:`      | `any`     | Вопрос к блоку кода или логике задачи (может быть как техническим, так и контекстуальным).                  | `// # QUE: Должна ли кнопка «Отмена» сбрасывать все поля формы?`                                                  |
| `# ANS:`      | `any`     | Ответ на `# QUE:`, отсылка к теории, шаблону, спецификации или бизнес-правилам.                             | `// # ANS: Да, по требованиям из ТЗ v2.1`                                                                         |
| `# BACKLOG:`  | `any`     | Задача или улучшение, принятое в список будущих доработок (может быть техническим или продуктовым).         | `// # BACKLOG: Продумать кэширование для этого запроса`<br>`// # BACKLOG: Пересмотреть алгоритм поиска в таблице` |


> 💡 Чтобы явно разделить слои в длинных заметках, можно использовать внутренние подметки:  
> `// # NOTE: [CONTEXT] Шахматы...`  
> `// # NOTE: [TECH] Мьютекс...` (опционально, в справочнике не фиксируются).

## Класс 2. Результативные теги (галочки / закладки)

> Могут использоваться без пояснения — просто как маркер статуса.

| Маркер     | Значение                                                                                                                    | Пример использования                                  |
| ---------- | --------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| `# DONE:`  | **Финальная точка.** Готово, протестировано, в продакшне. Ставится **в конце** блока.                                       | `// # DONE: Валидация email через regex`              |
| `# MAKED:` | Реализовано, но не факт, что протестировано или в продакшне. Промежуточная галочка для *всего блока*.                       | `// # MAKED: Черновой парсер даты`                    |
| `# FIXED:` | Исправление по `# FIXME:` выполнено. Ставится *внутри блока* кода – от 1 до нескольких раз (при исправленных недоработках). | `// # FIXED: Убрал утечку памяти, контекст очищается` |
| `# STUB:`  | Заглушка / фундамент для будущей логики; содержание кода этого маркера сейчас не используется.                              | `// # STUB: Метод пока возвращает null`               |
| `# INIT:`  | Создана структура / заготовка, наполнение будет позже.                                                                      | `// # INIT: Объявлен интерфейс репозитория`           |
| `# PROC:`  | Блок в процессе разработки (Work In Progress). Удаляется перед слиянием в основную ветку.                                   | `// # PROC: Дописываю обработку ошибок`               |
| `# TMP:`   | Временный код, который будет удалён после проверки идеи.                                                                    | `// # TMP: Жёстко зашитый ID для теста`               |
| `# HOLD:`  | Работа приостановлена; блок может вернуться в разработку позже.                                                             | `// # HOLD: Ждём обновления библиотеки`               |
| `# ARCHV:` | Архив. Код оставлен для истории, возвращать в работу не планируется.                                                        | `// # ARCHV: Первая версия парсера`                   |
| `# SOLVED:` | Аналитическое решение принято; закрывающая метка перед переходом к реализации. Завершает цикл анализа *концепта* решения и обсуждения. | `// # SOLVED: Выбран асинхронный подход, приступаем к коду` |

## Класс 3. Побудительные теги (действия)

> Указывают, что нужно сделать. Пояснение желательно. Открывают дальнейшее решение

| Маркер      | Значение                                                                 | Пример использования                                      |
|-------------|--------------------------------------------------------------------------|-----------------------------------------------------------|
| `# TODO:`   | Точно сформулированная задача на будущее.                                | `// # TODO: Добавить обработку ошибок сети`               |
| `# FIXME:`  | Код работает, но содержит известный баг или неоптимальность. Требует исправления. | `// # FIXME: При большом числе записей будет тормозить` |
| `# REFACT:` | Требуется рефакторинг (переименование, выделение функции и т.п.).        | `// # REFACT: Вынести дублирующийся цикл в утилиту`       |
| `# PLAN:`   | Зафиксированный план действий: что и зачем будем менять по шагам.        | `// # PLAN: Сначала вынести валидацию в отдельный хелпер` |
| `# MAKEME:` | Прямое указание реализовать конкретную функцию.                          | `// # MAKEME: Дописать парсинг даты из ответа API`        |
| `# DEBUG:`  | Код только для отладки, не должен попасть в продакшн.                    | `// # DEBUG: console.log('Значение:', data);`              |
| `# KEEP:`   | Категорическое указание не удалять этот блок (даже если кажется ненужным). | `// # KEEP: Используется в тестах через рефлексию`        |
| `# REDEF:` | Требуется *мысленный рефакторинг*, т.е. переопределение роли блока и его функционала (расширить его/сократить/переформировать и т.д.) | `// # REDEF: функцию get_dataset_dict() переместить из get_dict() в класс Data и добавить аргументы.` |
| `# REPLACE:` | Замена части решения/блока кода на другую | `// # REPLACE: parse_page заменено на 2 функции: parse_html_page и parse_files`<br>`// # REPLACE: get_today_on_schedule -> *get_shifts_for_date*`|

## Теги чисто для документации и черновиков (MINDWORK)

> Эти теги предназначены для `.md`-файлов, аналитических записок, черновиков.  
> Они подразумевают развёрнутое описание и часто формируют отдельный документ.

| Маркер    | Назначение                                                                                                                              | Пример использования                                                                                                  |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `# GROK:` | Глубокое погружение в сложную логику или взаимосвязь идей. Может разрастись до целой онтологии.                                         | *В аналитической заметке:* «# GROK: Как связаны авторизация и кэш»                                                    |
| `# DEEP:` | Отсылка к детальному изучению конкретного аспекта (спецификация, RFC, внешняя документация). Можно использовать в коде как короткую ссылку. | `// # DEEP: см. docs/architecture.md#кэширование`<br>`// # DEEP: docs/математическое_моделирование_сплошных_сред.pdf` |

## Использование в коммитах

Формат сообщения коммита: `# TAG: краткое описание`

| Маркер      | Значение в коммите                  |
| ----------- | ----------------------------------- |
| `# INIT:`   | Первичное создание. В отличие от `ADD` не требует наполнения                  |
| `# ADD:`    | Добавление функциональности / файла |
| `# UPD:`    | Обновление                          |
| `# RENAME:` | Переименование                      |
| `# FIX:`    | Исправление ошибки                  |
| `# REFACT:` | Рефакторинг                         |
| `# DOCS:`   | Изменения в документации            |
| `# TMP:`    | Временное сохранение состояния      |
| `# MERGE:`  | Слияние веток                       |

## Общие рекомендации

- **Поиск:** `Ctrl+F` и имя тега (например, `# TODO:`) быстро перемещают по ключевым точкам.
- **Жизненный цикл:**  
  - `# PROC:` и `# DEBUG:` удаляются перед слиянием в основную ветку.  
  - `# QUE:` заменяется на `# ANS:` или удаляется.  
  - `# TODO:` / `# FIXME:` → после выполнения заменить на `# DONE:` / `# FIXED:`.
- **DONE — финал:** всегда ставьте `# DONE:` **в конце** блока, как завершающую точку.
- **Слои пояснений:** для явного разделения используйте столбец «Слой» или неформальные подметки `[TECH]`, `[CONTEXT]` внутри комментария.
- **Документация:** `# GROK:` и `# DEEP:` предпочтительны в отдельных `.md` файлах; в коде `# DEEP:` может служить ссылкой.
>[!important]
> Маркеры не диктуют жёсткий порядок — это гибкий инструмент.
> 
> Для каждой отдельной подзадачи можно пройти путь:
> 
> `#ANALYZED:` (поняли суть) → `#SOLVED:` (приняли решение) → `#MAKEME:/#TODO:` (ставим задачу на код) → `#MAKED:` (реализовано) → `#DONE:` (готово).
> 
> Но в любой момент можно вернуться к анализу (ALIGN), добавить `#QUE:`/`#ANS:`, переосмыслить `#HACK:` и даже передумать, поставив `#HOLD:` или `#ARCHV:`.
Теги служат желательными указателями, а не рельсами. Это «дорожные знаки», а не расписание поездов.
